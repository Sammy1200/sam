# 上架、余额与悬浮窗

这份文档用于解释当前主线里的上架规则、余额规则和悬浮窗职责。重点不是线程过程，而是“这些规则现在为什么存在”。

## 上架流程在系统中的位置

上架不是独立子程序，而是被插在主流程关键位置：

- 启动进入交易行后，先做预上架
- 换号 / 切换完成后，先做预上架
- 抢购运行期间，按间隔尝试周期上架

这样做的目的很明确：

- 新账号进入抢购前，先把库存处理到当前轮次状态
- 运行中再做补充上架
- 不让换号后直接裸进入抢购

## 余额识别的“确认 / 未确认”机制

余额链路不是“识别到什么就立刻当真”，而是有确认态区分：

- 新确认值：OCR/模板结果可信，可作为新的有效余额
- 沿用旧值：当前识别不可信，继续沿用上次有效余额
- 待确认：当前还没有形成稳定有效余额

悬浮窗里的 `新`、`沿`、`待确认` 是展示态前缀，不是 canonical 状态枚举。

## 余额异常下跳保护为什么存在

当前系统启用了“异常大下跳保护”，规则是：

- 只拦突然大幅下降
- 不拦上涨
- 只在上一次有效余额 `<= 1.1 亿` 时启用
- 当前阈值是 `10000000`

存在原因是：

- 低余额阶段 OCR 抖动更容易误触发“余额不足”
- 一次错误识别不应该覆盖已经确认过的有效余额

## 余额不足判定口径

当前余额不足阈值是 `10000000`。

当有效余额低于阈值时，系统会：

- 结束当前轮
- 写入结束状态
- 触发后续调度或切换

这里使用的是“有效余额”，不是任意一次 OCR 原始字符串。

## 上架前余额门槛

当前上架前有一个独立门槛：

- 每次真正进入上架流程前，直接使用最后一次有效余额判断
- 最后一次有效余额 `> 4 亿` 时，本轮直接跳过上架

换号后首次上架还有额外规则：

- 必须先走完整正常链路并回到交易行
- 再强制识别一次当前余额
- 如果这次余额仍 `> 4 亿`，本轮后续上架都跳过

这条规则存在的原因是：

- 避免高余额账号重复做无效上架动作
- 只影响上架执行与否，不增加抢购主循环复杂度

## 周期上架停用机制

当前上架还有一个“本轮停用”开关：

- 如果连续翻页未找到道具达到阈值，会停用本轮后续自动上架

目的不是全局禁用上架，而是避免当前轮次在明显无货时不断做无效尝试。

## 悬浮窗当前主要职责

悬浮窗当前主要做 4 件事：

- 展示状态
- 展示计分板
- 展示日志
- 处理 F12 暂停 / 恢复

它不应承担：

- 抢购决策
- 数据真源判定
- 复杂业务写库逻辑

## 悬浮窗为什么坚持“显示层优先”

当前要求把增强优先放在显示层，是因为：

- overlay 需要保持稳定、轻量、可恢复
- 业务逻辑塞进 overlay 后，会让恢复、Mini 模式和日志刷新一起变脆
- F12 暂停/恢复已经需要做最小写回，再继续堆业务会扩大风险

## 日志与悬浮文案约束

当前悬浮窗相关文案有硬约束：

- 全部使用简体中文
- 新增或修改的悬浮窗日志宽度不超过 12 个中文字符
- 正常模式必须保留计分板区域和日志区
- Mini 模式只能隐藏组件，不能销毁组件

这些约束的目标是：

- 保持实时可读
- 避免恢复正常模式后组件丢失
- 避免日志撑坏布局
