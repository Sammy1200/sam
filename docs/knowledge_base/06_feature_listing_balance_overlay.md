# 上架、余额与悬浮窗

这份文档用于解释当前主线里的上架规则、余额规则和悬浮窗职责。重点不是线程过程，而是“这些规则现在为什么存在”。

## 上架流程在系统中的位置

上架不是独立子程序，而是被插在主流程关键位置：

- 启动进入交易行后，先做预上架
- 换号 / 切换完成后，先做预上架
- 抢购运行期间，按间隔尝试周期上架

这样做的目的很明确：

- 新账号进入抢购前，先把库存处理到当前轮次状态
- 运行中再做补充上架
- 不让换号后直接裸进入抢购

## 余额识别的“确认 / 未确认”机制

余额链路不是“识别到什么就立刻当真”，而是有确认态区分：

- 新确认值：OCR/模板结果可信，可作为新的有效余额
- 沿用旧值：当前识别不可信，继续沿用上次有效余额
- 待确认：当前还没有形成稳定有效余额

悬浮窗里的 `新`、`沿`、`待确认` 是展示态前缀，不是 canonical 状态枚举。

饰品模式使用专用金币余额区域 `(1546, 12, 142, 40)`，但仍沿用正常余额模板识别链路。由于金额长度会变化，这个区域内有时会包含金额前方的金币图标；识别前必须忽略左侧金币图标块，不能把图标误识别成金额开头数字。饰品金币区域右侧偶发孤立噪点时，只在噪点前方分块能组成带单位的合法金额时才裁掉噪点；不能形成合法金额时返回 `None`，不猜结果。

离线评测入口是 `scripts/eval_balance_real.py`。`samples/jinbi` 会按饰品金币区域自动评测，文件名支持普通标准答案，也支持 `不识别，4.821亿`、`错误识别成71.5889亿，真实-1.5889亿` 这类描述式命名；带 `--search` 时会先批量搜索金币图标与尾部噪点相关参数。

## 余额不足判定口径

当前余额不足阈值是 `10000000`。

当有效余额低于阈值时，系统会：

- 结束当前轮
- 写入结束状态
- 触发后续调度或切换

这里使用的是“有效余额”，不是任意一次 OCR 原始字符串。

## 上架前余额门槛

当前上架前有一个独立门槛：

- 每次真正进入上架流程前，直接使用最后一次有效余额判断
- 最后一次有效余额 `> 8 亿` 时，本次直接跳过上架
- “首次启动账号”与“换号后首次上架”都会先在交易行额外识别一次余额；若识别结果 `> 8 亿`，则只取消这次上架，不取消本轮后续流程

这条规则存在的原因是：

- 避免高余额账号重复做无效上架动作
- 只影响当前这次上架执行与否，不增加抢购主循环复杂度

## 每账号每轮上架上限

当前每个账号每轮还有一个固定上限：

- 本轮上架成功达到 `100` 次后，停止本轮后续自动上架
- 计数直接复用现有的 `round_listing_success_count`
- 这个上限只在当前账号当前轮次内生效；切换到下一个账号后重新从 0 开始

## 上架提交验证失败恢复

普通上架提交后如果验证失败，会先处理首次提示弹窗：

- 先在 `MONITOR_TISHI` 区域识别 `logo/shangjia/tishi.png`
- 在上架页面命中并点击消除成功后，直接按本次上架成功处理
- 未命中时，才进入提交按钮补点与局部场景恢复链路

这条规则用于避免首次上架提示弹窗被误判为上架验证失败。

## 容量已满后的下架保护

当前上架链路在识别到“容量已满”后，不再直接把所有满位都当成可下架对象，而是先看倒计时：

- 先检查 `(480, 140)` 到 `(585, 175)` 的倒计时区域
- 只判断小时两位是否为 `46/47`
- 高置信判定“小时不等于 `46/47`”时，执行下架
- 高置信命中小时 `46/47` 时，不下架，按原链路直接收口
- 如果识别结果是 `None`，也执行下架；当前 `46/47` 命中已稳定，`None` 不再作为保守跳过分支

下架链路当前还有两个附加约束：

- 每次执行下架前，会先额外等待 `500ms`
- 每次下架后，会先固定等待 `500ms` 再验证“可上架数量是否 +1”
- 若第一次未 `+1`，会按 `1` 秒间隔继续重试 `3` 次
- 若重试后仍未 `+1`，则跳过这次校验失败并继续后续操作，不再直接暂停
- 只有容量校验 `confirmed` 时，才允许把道具库存 `+1` 并同步 SQLite
- 若一次下架校验已确认成功，则下一次执行下架前还会额外等待 `1.5` 秒
- 如果上下架反复循环，系统会暂停并提示，避免无限振荡

这条规则存在的原因是：

- `46/47` 是当前上架链路里的保留窗口，不能被误杀
- 当前只放了 `46/47` 模板，且实机已确认 `46/47` 能命中；因此 `None` 更适合按“不是 46/47”处理
- 可上架数量 `+1` 仍是优先成功判据，但当前不再把这一步当作阻断性硬失败

## 周期上架停用机制

当前上架还有一个“本轮停用”开关：

- 如果连续翻页未找到道具达到阈值，会停用本轮后续自动上架

目的不是全局禁用上架，而是避免当前轮次在明显无货时不断做无效尝试。

## 悬浮窗当前主要职责

悬浮窗当前主要做 4 件事：

- 展示状态
- 展示计分板
- 展示日志
- 处理 F12 暂停 / 恢复

F12 暂停后的参数窗支持按分钟设置自动恢复倒计时：点击应用后，参数窗收起为标题条并显示 `恢复 HH:MM:SS`；倒计时归零时复用现有 F12 恢复逻辑，手动 F12 恢复会取消本次倒计时。

它不应承担：

- 抢购决策
- 数据真源判定
- 复杂业务写库逻辑

## 悬浮窗为什么坚持“显示层优先”

当前要求把增强优先放在显示层，是因为：

- overlay 需要保持稳定、轻量、可恢复
- 业务逻辑塞进 overlay 后，会让恢复、Mini 模式和日志刷新一起变脆
- F12 暂停/恢复已经需要做最小写回，再继续堆业务会扩大风险

## 日志与悬浮文案约束

当前悬浮窗相关文案有硬约束：

- 全部使用简体中文
- 新增或修改的悬浮窗日志宽度不超过 12 个中文字符
- 计分板滚动/兜底文本显示宽度不超过 15 个中文字符，即宽度 30；超宽时简化显示
- 正常模式必须保留计分板区域和日志区
- Mini 模式只能隐藏组件，不能销毁组件

这些约束的目标是：

- 保持实时可读
- 避免恢复正常模式后组件丢失
- 避免日志撑坏布局

## 余额不足后的补金币判定
当前 `余额不足` 不再是一命中就直接换号，而是先补做一次最新余额刷新：

- 固定顺序是“返回古墓大厅 -> 尝试领取金币 -> 返回交易行 -> 重新识别余额”
- 若金币入口未命中，解释为“没有金币可领取”，不微信推送，直接继续原换号流程
- 若补金币后余额恢复到阈值以上，则取消本次换号，继续抢购循环
- 若补金币后仍然余额不足，或中途返回古墓、金币链、返回交易行、余额识别失败，则继续按原余额不足换号逻辑收口
- 一旦最终仍然落到正式状态 `余额不足`，它会和 `账号限制 / 抢购时长已到` 一样纳入限制类冷却：写入 `last_limit_time`、网页显示冷却倒计时、可运行时间归 `0`、冷却结束后自动恢复为 `已准备`

## 未知页面的回古墓恢复
当前抢购主循环遇到未知页面时，新增了一层恢复动作：

- 先尝试返回古墓大厅 `3` 次
- 若成功回到古墓大厅，则立刻返回交易行并继续当前循环
- 只有 `3` 次都失败时，才回落到现有 `unknown_page_count` 未知页面治理
- 这条规则只增加恢复机会，不改变现有未知页面暂停/推送阈值
