# 执行位调度、切区与换号

这份文档用于解释当前系统怎么做执行位调度、同账号切区、跨账号换号、昵称校验和失败治理。重点是“现在怎么工作”，不是历史怎么演变到今天。

## 执行位是什么

当前系统以执行位组织主流程：

- 默认执行位数量是 8
- 每个执行位会映射到一个大区索引
- 4 个大区坐标在 `config.SERVER_COORDS`
- 执行位到大区的映射在 `config.EXECUTION_SLOT_SERVER_COORD_INDEXES`

执行位主要用于：

- 启动器识别后自动定位当前账号上下文
- 解析下一跳调度目标
- 在网页和悬浮窗中定位当前账号所在流程位置

## 默认模式的启动调度

默认回车启动时，系统做的是：

1. 从启动器画面识别当前执行位
2. 先把这个执行位作为昵称提示，去 canonical 读取账号记录
3. 如果昵称本身是数字或未直接命中，会按执行位兼容读取
4. 读到 canonical 记录后，得到真实昵称和当前执行位
5. 再按执行位自动推出目标大区
6. 沿启动器链进入游戏和交易行

所以默认模式不是人工选账号，而是“识别执行位 -> 读库 -> 推出账号上下文 -> 自动进链路”。

补充一条当前启动页识别规则：

- `hepingjingying.png` 现在除了用于账号登录后的切号结果确认，也参与“当前是否仍在启动页”的判断
- 当前固定同时使用两个识别区域：
  - 主区域命中：视为启动页处于正常口径
  - 次区域命中：视为当前仍在启动页，但窗口不是全屏
- 若退出游戏后迟迟未识别到启动页，会先尝试通过 Win32 把标题包含 `WeGame` 的窗口拉到前台，再继续后续模板识别
- 点击账号列表后若首次未匹配到 `qiehuan.png`，会先尝试把 `WeGame` 拉到前台，额外等待 `1` 秒，再重新点击账号列表重试一次切换账号入口识别
- 账号输入校验首次失败后，会重新点击输入框、重新输入账号并重新校验；最多补重试 `3` 次，仍失败才进入现有推送出口
- 一旦命中次区域，不再直接最大化，而是先点击 `hepingjingying.png` 的命中中心点，再执行恢复全屏操作
- `qidong.png` 仍保留，但现在更偏向“启动按钮已就绪”的确认，而不是唯一的启动页判断依据
- 任何需要在启动页执行点击的任务，首次点击前都必须先识别 `hepingjingying.png`；若未识别到会先尝试把 `WeGame` 拉到前台再重试，仍失败则进入现有失败推送链
- 启动页点击统一前置守卫已接入：切换账号入口、切号登录后的启动页承接点击、打开大区列表、选择目标大区、点击启动游戏
- 正常启动链在进入昵称模板校对前，会先把悬浮窗切到 mini 收起态，避免遮挡昵称识别区域
- 空格弹窗首次识别失败后，不再立即推送；会先尝试通过 Win32 把标题包含 `和平精英模拟器高清版` 的游戏窗口拉到前台并最大化，再重新识别空格弹窗；后续按 `10` 秒间隔补重试 `20` 次，每次仍未识别到时也会尝试拉起游戏窗口后短识别，全部失败后才进入现有微信推送出口

## 启动页上架模式

启动器现在还多了一条独立入口：`启动页上架模式`。

这条链路的目标不是进入抢购，而是：

1. 按执行位 `1 -> 8` 顺序扫描 canonical SQLite
2. 只筛余额 `< 5 亿` 且状态不是 `账号限制` 的账号
3. 进入目标执行位后，只做上架批次，不进抢购主循环
4. 每个账号结束后先正常下号，再继续找下一个候选账号
5. 当 `1-8` 全部扫描完成且没有剩余候选后，自动切回正常模式，选择“剩余可运行时间最少”的执行位继续正常换号上号抢购循环

这条模式和默认模式、临时模式的边界是：

- 不复用抢购主循环
- 不改默认模式的启动调度
- 不改临时模式的目标执行位切换逻辑
- 启动页上架模式的账号登录、换号、换区链路固定使用迷你悬浮窗，避免遮挡识别区域
- 启动页上架模式的进场昵称校验只确认执行位，不把账号状态写成 `运行中`
- 启动页上架模式下按 `F12` 暂停/恢复时，只最小写回 `本轮上架成功数`、`当前有效余额`、`当前道具库存`，不写账号状态、运行时间与其他字段
- 启动页上架模式中余额 `> 5 亿` 只作为停止本号继续上架的原因；按“余额超5亿”收尾时保留账号原状态，不改成 `已准备`
- 启动页上架模式命中 `翻页到底` 时，只结束本号本轮上架；账号状态保持原值，不改成 `已准备`
- 启动页上架模式进场后余额未识别、或批次返回其他异常/失败原因时，账号状态写为 `未知异常`
- canonical SQLite 中只要账号状态发生变化，就会立刻触发一次事件快照，同步到公网快照页

## 调度如何决定“切区”还是“换号”

当前调度逻辑按执行位边界区分两类情况：

- 非边界切换：同账号内跨区切换
- 边界切换：跨账号换号

当前固定边界是：

- `4 -> 5`
- `8 -> 1`

当命中边界时，系统会走换号链；否则只走同账号跨区链。

启动页上架模式则单独采用“两组账号”口径：

- `1-4` 为一组
- `5-8` 为一组

账号号本身不写死，统一来自本机 `local_switch_account_config.json`：

- `after_slot_8_account_id` 对应 `1-4`
- `after_slot_4_account_id` 对应 `5-8`

因此启动页上架模式当前的切换规则是：

- 首个候选执行位必须从登录页输入对应账号组
- 同账号组内切下一个执行位时，只换区，不重新输入账号
- 跨账号组时，再回登录页重新输入对应本机账号
- 全部候选扫描完成后，按 `1-8` 账号视图里的“剩余可运行时间”最少优先切回正常模式；若全部缺失，再回退到“冷却剩余时间”最少

## 当前已落地主体能力

当前主线已经落地的主体能力包括：

- 启动器识别执行位
- 按执行位和昵称读取 canonical 账号记录
- 同账号跨区切换
- 跨账号换号
- 换号后昵称模板校验
- 正常抢购链路昵称识别后，如果目标账号仍在冷却中，会停留选区页等待，mini 悬浮窗显示 `冷却 HH:MM:SS`
- 冷却等待结束后再点击启动游戏，并把账号状态写成 `运行中`
- 换号成功后若账号状态改成 `运行中`，会立刻触发一次公网快照同步
- 换号后先完整上架，再进入抢购
- 换号后清零跨账号残留计数器
- 关键失败出口统一暂停并推送

## 换号链的本机配置入口

换号所需的本机差异不直接硬编码在主业务里，而是从本机配置层读取，主要包括：

- 边界换号使用的真实账号 ID
- 上架价格
- 昵称模板目录
- 昵称识别区域
- 昵称匹配阈值

因此处理换号问题时，先区分是：

- 本机配置问题
- 还是主流程逻辑问题

## 昵称校验怎么工作

昵称校验当前依赖：

- 模板目录
- 本机识别区域
- 本机匹配阈值

这些值通过 `local_switch_account_config.py` 从真实本机配置加载。当前设计目的是：

- 不把不同电脑的显示差异硬编码到主线逻辑
- 让模板、区域、阈值跟着本机环境走
- 线程 6 切区后若首次昵称模板匹配失败，先从“打开大区列表”重新开始，而不是只在原地重复模板匹配

线程 6 的切区后昵称模板校验当前还有一条固定恢复规则：

- 首次昵称模板匹配失败后，不立即暂停
- 必须从“打开大区列表 -> 选择目标大区 -> 昵称模板校验”重新开始
- 额外重试 `3` 次
- 任意一次成功就继续后面的恢复进场链路
- `3` 次都失败后，才进入现有暂停、推送、停机出口

## 失败治理怎么收束

当前切换链的失败治理不是“简单返回 False”，而是统一走失败出口：

- 记录中文日志
- 推送消息
- 暂停脚本
- 尽量保留现场，等待人工确认

这意味着：

- 切换问题先看失败步骤名
- 再看对应等待参数、模板、坐标、本机配置

## 当前已知可接受风险

- 这条链路对 UI 模板、坐标和等待参数高度敏感。
- 本机模板资源和识别区域不一致时，容易出现“逻辑没坏，但本机识别失败”的问题。
- 执行位种子记录只是建档兜底，不应误认为真实账号资料。

## 明确未纳入范围

- 不把换号后“先上架再抢购”的顺序改掉。
- 不把步骤 6-8 随意重排。
- 不把昵称模板校验替换成任意别的主键语义。
- 不把临时模式重新接回 canonical 单账号主表写回。

## 换号前最新余额刷新
当前切号调度前又新增了一条固定收口规则：

- 只要本轮已经命中 `need_switch_server=True`，真正执行退出游戏换号前，都先尝试一次“返回古墓大厅 -> 尝试领取金币 -> 返回交易行 -> 最新余额识别”
- 若领取金币成功，关闭金币面板固定顺序是“交叉执行右上角关闭点点击 + Esc -> 点击 `(1890, 20)` -> 点击 `(830, 690)` -> 用古墓大厅模板确认回到古墓大厅”
- 若这次最新余额刷新成功，先把最新余额写回 SQLite 真源，再额外触发一次事件快照，尽快同步到网页
- 若金币入口未命中，解释为“没有金币可领取”，不微信推送，直接继续原换号流程
- 若不是“无金币可领”而是返回古墓、金币链中途、返回交易行或余额识别失败，则不再微信推送“未识别最新余额”，只记本地日志后继续换号
