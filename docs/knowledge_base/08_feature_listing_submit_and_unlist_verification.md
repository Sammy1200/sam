# 上下架成功验算

这份文档用于说明当前主线里“上架成功 / 下架成功”如何判定，以及容量识别现在负责什么、不再负责什么。

## 核心结论

- 上架成功不再以容量变化作为主判据
- 下架成功不再以容量 `+1` 作为主判据
- 容量识别现在只用于判断“后面还要不要继续上架 / 是否需要恢复空位”
- 上架成功后库存仍然 `-1`
- 下架成功后库存仍然 `+1`

## 上架成功怎么判

当前口径：

1. 输入价格并完成验算
2. 在区域 `1414,779 -> 1519,821` 识别 `logo/shangjia/shangjia1.png`
3. 找到后点击图片中心
4. 再次识别同一模板
5. 第二次未识别到，即判定本次上架成功

如果第一次就没识别到，或者第二次还识别到，按现有失败链处理。

## 下架成功怎么判

当前口径：

1. 点击下架按钮
2. 在区域 `1040,672 -> 1144,718` 识别 `logo/shangjia/queding2.png`
3. 找到后点击图片中心
4. 再次识别同一模板
5. 第二次未识别到，即判定本次下架成功

如果第一次没识别到确认弹窗，或者第二次仍然识别到确认弹窗，按现有下架失败链处理。

## 为什么不再用容量变化判成功

实机里会出现一种并发情况：

- 正在执行上架或下架动作
- 同一时间已有别的道具被卖掉
- 结果容量数字不按预期的 `+1 / -1` 变化

这时如果仍然用容量变化作为成功主判据，就会把真实成功误判成失败。

## 容量识别现在负责什么

容量识别现在只负责：

- 当前还有没有空位继续找道具上架
- 当前是不是容量已满，需要进入恢复链
- 后续流程还要不要继续上架

容量识别不再负责：

- 判定刚才那次上架是否成功
- 判定刚才那次下架是否成功

## 库存与最小同步

- 上架成功后，继续沿用现有逻辑：
  - `round_listing_success_count += 1`
  - `baseline_item_count -= 1`
  - 立即做最小同步
- 下架成功后，继续沿用现有逻辑：
  - `baseline_item_count += 1`
  - 立即做最小同步

这次没有改状态写库、微信推送、模式分流和上架次数上限规则。

## 下架成功后的容量处理

- 下架成功后，不再立即读取容量
- 只有在后续“不满足下架条件 / 需要判断是否继续上架”时，才读取容量

这样做的目的，是避免把容量数字的瞬时异常再次误当成下架失败。
